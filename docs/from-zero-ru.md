# С нуля: что сломалось, что поправили и что читать дальше

Этот файл — **дорожная карта для человека**, который поднимает бота на VPS и хочет понять контекст отладки (Telegram, прокси, конфиг, Git). Он **дополняет** [`README.md`](../README.md) (там — команды, деплой, архитектура). Раздел **«Темы для самостоятельного изучения»** (§5) — что учить в стороне от репозитория, чтобы понимать типичные ошибки и как их чинить.

---

## 1. Что это за программа (очень коротко)

Процесс **`python main.py`** делает две вещи **параллельно**:

1. **Поток Telegram** — long polling к Bot API: команды в группах (`/notify_here` и т.д.), личка админа (`/status`, `/topics`).
2. **Главный поток** — периодически логинится на **AO3**, читает **Inbox**, находит новые **комментарии**, шлёт сообщения в подписанные **топики** Telegram.

Состояние (какие комментарии уже видели, какие чаты подписаны) хранится в **`bot_state.json`** рядом с проектом.

Имеет смысл один раз просмотреть схему в README → раздел **«Архитектура»**.

## 2. Что было «не так» (типичная история на VPS)

Ниже не приговор вашему серверу, а **объяснение симптомов**, которые уже встречались в логах.

### 2.1. `Network is unreachable` до `api.telegram.org`

С VPS **не устанавливалось прямое HTTPS-соединение** до хостов Telegram (часто провайдер/маршрутизация/фильтрация). Ошибка вида **`[Errno 101] Network is unreachable`** означает: программа пыталась открыть TCP к Telegram **напрямую**, без обходного пути.

**Проверка:** с сервера `curl -I https://api.telegram.org/` — если «висит» или ошибка, а через локальный прокси (`curl -x socks5://127.0.0.1:PORT ...`) ответ есть — значит нужен **прокси именно для запросов бота к Bot API**.

В коде прокси включается через **`TELEGRAM_PROXY_URL`** или **`[TELEGRAM] PROXY_URL`** в `config.ini` — см. [`bot_client.py`](../bot_client.py), функция `_apply_telegram_proxy`.

Важно: **AO3** этим прокси **не проксируется** — до `archiveofourown.org` идёт отдельное соединение с VPS.

### 2.2. Прокси работал в `curl`, но не в боте

Бывало так:

- sing-box слушает **`127.0.0.1:1234`**, `curl -x socks5://127.0.0.1:1234 https://api.telegram.org/` успешен;
- бот всё равно лезет на **`api.telegram.org` напрямую** и падает.

Причины:

1. В конфиге процесса **не было URL прокси** — тогда в логе **нет** строки  
   `[Telegram] Bot API через прокси: ...`  
   (она пишется при старте в [`bot_client.py`](../bot_client.py).)

2. В оболочке Bash выполнили  
   `TELEGRAM_PROXY_URL=socks5://127.0.0.1:1234`  
   **без** `export`. Так задаётся переменная **только для самой оболочки**, дочерний процесс **`python`** её **не наследует**. Нужно либо `export TELEGRAM_PROXY_URL=...`, либо одной строкой  
   `TELEGRAM_PROXY_URL=... python main.py`, либо файл **`.env`** / **`config.ini`** (см. ниже про конфиг).

### 2.3. Ошибки входа в AO3 при живой сети к Telegram

Сообщение «Не удалось войти в AO3» в логе **не всегда** означает неверный пароль. Если HTTPS до AO3 обрывается (**SSL EOF**, таймауты), логин тоже не пройдёт — это **другой маршрут**, не прокси Telegram.

### 2.4. Админ: «chat_id не определён», таймер отчётов отключён

Для периодических отчётов в ЛС боту нужен **числовой chat id** админа. Его можно задать явно как **`ADMIN_TELEGRAM_USER_ID`** / **`[ADMIN] TELEGRAM_USER_ID`** — тогда не нужен запрос **`getChat`** по `@username`. Если до Bot API без прокси не достучаться или `getChat` падает, **username одного мало** — надёжнее **числовой id**.

### 2.5. Утечки в Git

В репозиторий нельзя коммитить **`config.ini`**, **`.env`**, **`bot_state.json`** (там могут быть **chat_id**, подписки, связка с AO3). В проекте **`bot_state.json`** раньше мог попасть под Git — его нужно было убрать из индекса и добавить в **`.gitignore`**. Если что-то уже улетело на GitHub **публично**, разумно **сменить токен бота** и пересмотреть чувствительные данные.

### 2.6. Токен бота в логах

Строки ошибок urllib/TeleBot иногда содержат **полный URL с токеном**. Такой токен считается скомпрометированным — в [@BotFather](https://t.me/BotFather) делают **Revoke** и подставляют новый в конфиг.

## 5. Темы для самостоятельного изучения (сеть, ошибки, починка)

Ниже темы по **слоям**: обычно так и диагностируют проблемы на VPS.

### 5.1. Сеть на практике (Linux / VPS)

- **IP, TCP, порты** — что значит открыть соединение на `host:443`.
- **Маршрутизация и «нет маршрута»** — когда видите **`Network is unreachable` / errno 101**: часто «до этого адреса из этой сети не знают, куда слать пакеты», не обязательно «сервер лежит».
- **DNS** — как имя превращается в IP; разница между резолвом на машине и резолвом **на стороне прокси** (это про `socks5` vs `socks5h`).
- **Инструменты:** `curl`, `ss` / `netstat`; `ping` не всегда показателен для HTTPS; по желанию `traceroute` / `mtr`.

Понимание слоя объясняет: почему «один сайт открывается, другой нет», почему помогает локальный SOCKS на `127.0.0.1`.

### 5.2. HTTPS и TLS (без излишней теории)

- **Что даёт TLS:** шифрование канала, проверка сертификата (упрощённо).
- Типичные симптомы: **`SSL: UNEXPECTED_EOF`**, обрыв во время рукопожатия — часто **не «неверный пароль сайта»**, а обрыв / фильтрация на пути или странный посредник.
- Уметь отличить **ошибку до установления TLS** (сеть) от **ошибки после** (HTTP-коды, редирект на логин и т.д.).

Это помогает не путать проблемы до **AO3** с проблемами до **Telegram** (разные хосты, разные пути).

### 5.3. Прокси: HTTP и SOCKS

- **HTTP-прокси** и метод **CONNECT** для HTTPS (идея «туннель до целевого хоста»).
- **SOCKS5** — прокси пересылает TCP «куда сказали»; TLS к сайту часто идёт **поверх** уже установленного SOCKS-туннеля.
- **`socks5` vs `socks5h`:** где выполняется резолв имени — локально или через прокси.
- Проверка: **`curl -x socks5://...`** или **`-x http://...`**.

Связь с проектом: sing-box даёт локальный SOCKS; в коде прокси задаётся **только для клиента**, который его использует (Telegram Bot API через `requests`), не «для всей системы автоматически».

### 5.4. Переменные окружения и процессы

- Разница между **переменной в shell** и **environment дочернего процесса** — тема **`export` в Bash** и однострочный запуск `VAR=value команда`.
- Как **systemd** передаёт переменные: **`Environment=`**, **`EnvironmentFile=`**.
- Идея **`.env` + python-dotenv:** файл читает само приложение при старте.

После этого понятно, почему переменная «видна в терминале», но не в Python, и зачем не оставлять пустые `VAR=` в unit, если хотите fallback на INI / `.env`.

### 5.5. Стек Python для HTTP

- Библиотека **`requests`** и под капотом **urllib3**: пул соединений, параметр **`proxies`**.
- Как **pyTelegramBotAPI** использует **`telebot.apihelper.proxy`** для запросов к Bot API.
- Для схемы **`socks5://`** у `requests` нужен **PySocks** (в зависимостях проекта).

Вывод: «`curl` через прокси работает» не означает, что любая программа ходит через прокси — нужно **явно** настроить тот клиент, который делает запрос.

### 5.6. Telegram на концептуальном уровне

- Что такое **Bot API** и базовый хост **`api.telegram.org`**.
- **Long polling** vs webhook (в этом боте — polling).
- **Токен бота** — секрет: не светить в логах, чатах и Git; при утечке — **Revoke** в BotFather.

### 5.7. Эксплуатация и безопасность

- Читать **логи** и трассировки: по тексту ошибки понять **целевой хост** (прямое соединение или ожидался прокси).
- **`.gitignore`**, что не коммитить: токены, **`bot_state.json`**, **`.env`**, **`config.ini`**.
- Базово **systemd**: **`WorkingDirectory`**, **`ExecStart`**, при необходимости **`After=`** для сервиса прокси.

### 5.8. Куда смотреть в документации (справочно)

| Тема | Где искать |
|------|------------|
| Bash, `export` | любой учебник Bash, раздел про переменные и окружение |
| systemd | `man systemd.unit`, `man systemd.service`; гайды по `EnvironmentFile` |
| curl, прокси | `man curl`, ключи `-x`, `--proxy` |
| TLS / HTTPS | вводные статьи «как работает HTTPS» (достаточно обзорного уровня) |
| Python requests + прокси | официальная документация Requests (Proxies), заметки про PySocks для SOCKS |
| SOCKS5 | краткие обзоры + эксперименты с `curl -x` |

### 5.9. Минимальный алгоритм диагностики «как у нас в логах»

1. Ошибка про **`api.telegram.org`** → прямой `curl`, затем **`curl -x socks5://127.0.0.1:…`**.
2. Ошибка про **`archiveofourown.org`** → отдельная проверка **`curl -I`** без Telegram-прокси (в коде AO3 не обязательно идёт через тот же прокси).
3. «Задал переменную в shell» → **`export`** или запись в **`.env` / `config.ini`**.
4. Токен попал в лог или в Git → **rotate** в BotFather, проверить `.gitignore`.

## 6. Мини-чеклист после `git clone` на сервере

1. `python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt`
2. Скопировать **`config.ini.example` → `config.ini`** и заполнить секреты **или** использовать **`.env`** (он подхватывается автоматически, если установлен `python-dotenv`).
3. Если Telegram без прокси не доступен — **`PROXY_URL`** или **`TELEGRAM_PROXY_URL`**, sing-box (или другой SOCKS) уже слушает локальный порт.
4. Запуск: **`python main.py`** из корня проекта (или systemd).
5. В логе при успешном прокси для Telegram — строка **`Bot API через прокси`**.
6. **`config.ini`**, **`.env`**, **`bot_state.json`** в Git не коммитить.

---

## 7. Если снова что-то ломается

1. Открыть лог с **начала запуска** (без публикации токена в чаты).
2. Отделить проблему **Telegram** (ошибки на `api.telegram.org`) от проблемы **AO3** (`archiveofourown.org`).
3. Проверить, что конфиг реально загружен: в коде это всегда через **`config.load_config()`** и путь к `config.ini` рядом с [`config.py`](../config.py).

Удачной эксплуатации. При желании этот файл можно дополнять своими заметками под конкретный хостинг.
